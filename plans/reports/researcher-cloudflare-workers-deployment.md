# Research: Deploying Next.js 16 (App Router) to Cloudflare Workers — 2025/2026

Date: 2026-10-08. Project state checked: fresh `create-next-app` (Next 16.4.0, React 19.3.0,
Tailwind v4, Turbopack). Note: actual `next.config.ts` has `cacheComponents: true` and
`partialPrefetching: true` as **top-level** keys (promoted out of `experimental` in 16.3+);
only `agentFeedback: true` sits under `experimental`. No `middleware.ts`, no Route Handlers,
no Server Actions yet — adapter choice is unconstrained by existing code.

## 1. Adapter choice: @opennextjs/cloudflare vs @cloudflare/next-on-pages vs vinext

Three contenders, not two — Cloudflare shipped a third option (`vinext`) in 2026 that changes the
picture:

| Option | Status | Fit for this project |
|---|---|---|
| `@cloudflare/next-on-pages` | **Deprecated, repo archived 2026-10-01.** Edge-runtime only, last supported Next 13–14. | Reject outright. |
| `@opennextjs/cloudflare` (OpenNext) | Stable; adapter API GA since Next 16.2 (Mar 2026). Wraps real `next build` output, runs on Node.js-compat Workers runtime. Supports App Router, SSR, ISR, Route Handlers, Server Actions, Middleware (non-Node runtime), Image Optimization, Partial Prerendering, Turbopack. Known gap: Node Middleware (15.2+ runtime option) unsupported. Worker size cap 3 MiB (free)/10 MiB (paid) gzip. | **Recommended.** Mature, broad coverage, "the safer choice" per Cloudflare's own vinext docs. |
| `vinext` (`cloudflare/vinext`) | Cloudflare's new default recommendation for *new* projects, Vite-based reimplementation of the Next.js API surface. Explicitly **beta**: "not yet a drop-in replacement for every application or production workload." **Partial Prerendering and Cache Components (`"use cache"`) have incomplete implementation**; build-time image/font optimization not fully replicated; native modules (sharp/resvg/satori) can fail. | **Reject for now** — directly conflicts with this project's enabled `cacheComponents`/PPR flags, the exact area vinext admits is incomplete. |

**Why OpenNext wins here, despite Cloudflare pushing vinext as the new "default":** this project
has `cacheComponents: true` and `partialPrefetching: true` turned on from scaffold — these are
load-bearing Next 16 features, not incidental. vinext's own maintainers name Cache
Components/PPR as an open gap. OpenNext adapts the real `next build` output, so it inherits
Next's actual caching semantics rather than re-implementing them. No Node Middleware is used
in this repo, so OpenNext's one real gap doesn't bite. Revisit vinext once it leaves beta and its
Cache Components support is confirmed — not before.

## 2. Required config, wrangler setup, package.json scripts

**next.config.ts**: no changes needed for OpenNext compatibility of `cacheComponents` /
`partialPrefetching` (adapter lists "Partial Prerendering" and "composable caching" as
supported). Do add the OpenNext Cloudflare dev-helper for binding access:
```ts
import { initOpenNextCloudflareForDev } from "@opennextjs/cloudflare";
initOpenNextCloudflareForDev();
```

**wrangler.jsonc** (new file at repo root):
```jsonc
{
  "name": "my-app",
  "main": ".open-next/worker.js",
  "compatibility_date": "2024-09-23", // or later; must be >= this for nodejs_compat
  "compatibility_flags": ["nodejs_compat"],
  "assets": { "directory": ".open-next/assets", "binding": "ASSETS" }
}
```

**package.json scripts** to add:
```json
{
  "cf:build":   "opennextjs-cloudflare build",
  "cf:preview": "opennextjs-cloudflare preview",
  "cf:deploy":  "opennextjs-cloudflare deploy"
}
```
(`preview` runs a local Workers-runtime simulation via `wrangler dev`; `deploy` builds then
pushes with `wrangler deploy`.) Add `open-next.config.ts` at root per OpenNext's Cloudflare
scaffolding — generated by `npm create cloudflare@latest -- --framework=next` or by hand-adding
`@opennextjs/cloudflare` + `wrangler` as devDependencies to an existing app.

Note (unverified, flag as open question): Windows is **not** a guaranteed-supported dev
environment for the OpenNext Cloudflare adapter — docs recommend WSL/Linux. This machine is
Windows; confirm via WSL or accept CI-only builds before committing to this path.

## 3. Node.js API compatibility on Workers runtime

- `nodejs_compat` compatibility flag (with `compatibility_date >= 2024-09-23`) is **required** —
  it is what makes OpenNext's Node-targeted `next build` output runnable at all.
- Even with the flag, the Workers runtime does not fully replicate Node: no `fs`, no `path` (use
  Web-standard equivalents), Node's built-in `crypto` module is not provided (Workers expose
  **Web Crypto** instead) — this breaks libraries assuming Node crypto internals (e.g. some
  `jose` v5 code paths were reported incompatible).
- **Middleware**: runs in the **edge runtime**, not the Node-compat runtime, regardless of
  adapter. Anything importing Node-only `crypto` or `next/headers` `cookies()` (Node-only API)
  inside `middleware.ts` fails **at request time**, not at build time — this is the sharpest
  footgun. This project has no middleware yet; flag this constraint before one gets added for
  auth/session logic.
- **Route Handlers** run with full Node-compat + Cloudflare bindings (D1, R2, KV) access —
  better bindings access than middleware gets through OpenNext.
- **Server Actions**: supported, run in the Node-compat runtime like Route Handlers.
- **Image Optimization**: supported by OpenNext (unlike `next-on-pages`, which never supported
  it); uses Workers-compatible image resizing rather than Node `sharp`.

## 4. Experimental flags: keep or drop for Workers?

| Flag | Verdict | Why |
|---|---|---|
| `cacheComponents: true` | **Keep.** | OpenNext adapter explicitly lists Partial Prerendering + "composable caching" as supported; Next 16.4 (Oct 2026) made Cache Components the recommended-for-every-app default, no longer edge-case experimental. |
| `partialPrefetching: true` | **Keep.** | Client-side prefetch-shell caching, no server-runtime dependency; orthogonal to which server runtime executes the route. |
| `experimental.agentFeedback: true` | **Keep, but inert in prod.** | Purely a `next dev` DX feature (coding-agent error/workaround reporting) — has no runtime code path in `next build`/`next start` output, so it does not affect the Workers bundle either way. Safe to leave; could drop for a marginally cleaner prod config but there's no compatibility reason to. |

None of the three flags are vinext-incompatible concerns here since OpenNext is the pick — this
table would flip (cacheComponents/PPR → drop or treat as experimental-risk) only if vinext were
chosen instead, per vinext's own documented gap.

## 5. Env vars / secrets conventions

- **Local dev**: use Next.js's own `.env` / `.env.local` — not `.dev.vars` — as the default,
  because `next dev` only reads `process.env` from Next's env files; `.dev.vars` is only read by
  `wrangler dev`, so values placed there are invisible to the normal dev loop. Keep `.dev.vars`
  only for values you exclusively exercise through `wrangler dev`/`cf:preview`.
- **Per-environment overrides**: `.dev.vars.<env>` / `.env.<env>` for named Wrangler
  environments (staging, production-preview, etc.).
- **Production secrets**: `wrangler secret put <NAME>` — write-only once set (not readable back
  via CLI or dashboard). Use for API keys, DB credentials, signing keys.
- **Production non-secret vars**: plain `vars` block in `wrangler.jsonc`, or dashboard
  "Environment variables" — readable, versioned with the Worker, fine for things like feature
  flags or public config.
- **Hard rule**: never put secrets in the `vars` block of `wrangler.jsonc` (it's plaintext,
  typically committed) — only in `wrangler secret`. Gitignore `.dev.vars*` and `.env*` (already
  standard in `create-next-app`'s `.gitignore`).

## Ranked recommendation

1. **`@opennextjs/cloudflare`** — ship with this. Mature, GA adapter API since Next 16.2, full
   App Router/Server Actions/Route Handlers/Image Optimization/PPR coverage, no conflict with
   this project's enabled experimental flags, no middleware currently in the repo to collide
   with its one known gap.
2. **`vinext`** — revisit in 6–12 months once it exits beta and closes the Cache
   Components/PPR gap. Do not adopt now; it directly conflicts with flags this project already
   has on.
3. **`@cloudflare/next-on-pages`** — do not use; deprecated and archived.

Keep all three current experimental/stable flags (`cacheComponents`, `partialPrefetching`,
`agentFeedback`) as-is — none are blocked by the Workers runtime or the OpenNext adapter.

## Open questions / left uncovered

- Windows-as-dev-environment support for `@opennextjs/cloudflare` is explicitly "not
  guaranteed" per Cloudflare docs, and this machine is Windows — not verified firsthand whether
  `cf:preview`/`wrangler dev` work natively here or require WSL. Worth a quick spike before
  committing.
- Worker bundle size limits (3 MiB free / 10 MiB paid, gzip) are not yet a concern for this
  near-empty scaffold, but should be watched once dependencies grow (this is the single most
  common "worked in dev, failed at `wrangler deploy`" failure mode reported in community posts).
- Did not test-drive an actual `opennextjs-cloudflare build && wrangler deploy` cycle against
  this specific repo — findings are sourced from official docs + 2026 community reports, not a
  live deploy. Recommend a throwaway deploy spike to confirm before treating this as final.
